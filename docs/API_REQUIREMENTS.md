# INRFS Financer API Requirements

## Scope and source analysis

This contract is derived from every route, page, form, table, action, and mock dataset under `INRFS_FINANCER_FE/src`. The backend serves both the Financer Portal and its platform Admin Portal. All identifiers are UUIDs internally; human-readable numbers (`customerNumber`, `loanNumber`, `paymentNumber`, `invoiceNumber`) are generated by the server.

The current frontend is entirely mock/local-state driven. Its active financer pages are Dashboard, Customers, Loans, Payments, Interest Schedule, Due/Overdue, Customer Ledger, Notifications, Reports, Service Charge, Support, and Settings. Its active admin pages are Dashboard, Financers, Customers, Loans, Financer Usage, Service Charges, Monthly Billing, Collections, SMS Management, and Reports. Admin Payments, Notifications, Subscriptions, Settings, and Support exist but are not routed; Audit Logs has mock data/service scaffolding but no page.

## API conventions

- Base path: `/api/v1`.
- JSON uses camelCase and ISO-8601 UTC timestamps.
- Success envelope: `{ "success": true, "data": ..., "message": null, "traceId": "..." }`.
- Error envelope: `{ "success": false, "data": null, "message": "...", "errors": { "field": ["..."] }, "traceId": "..." }`.
- Paged data: `{ "items": [], "page": 1, "pageSize": 20, "totalCount": 0, "totalPages": 0 }`.
- List endpoints support `page`, `pageSize`, `search`, `sortBy`, `sortDirection`; relevant endpoints additionally accept status, financer, product, date, and overdue filters.
- Mutation requests may send `Idempotency-Key`. Financial mutations must be transactional.
- Financer users are tenant-scoped to their `financerId`. Platform roles can access all tenants according to permission claims.
- Deletes are soft deletes except refresh tokens/OTP records, which are revoked/expired rather than exposed.

## Authentication endpoints

| Method and route | Request | Response/use |
|---|---|---|
| `POST /auth/register/financer` | `{ fullName, businessName, mobile, email, city, state, password }` | Creates a financer owner and organization and returns a mobile OTP challenge |
| `POST /auth/login` | `{ email, password, portal }` | Validates credentials and status; returns an OTP challenge when MFA is required |
| `POST /auth/otp/request` | `{ challengeId?, destination, purpose }` | Rate-limited OTP challenge; stores only an OTP hash and expiry |
| `POST /auth/otp/verify` | `{ challengeId, code }` | JWT access token, rotating refresh token, expiry, user and permissions |
| `POST /auth/refresh` | `{ refreshToken }` | Rotates refresh token and returns a new token pair |
| `POST /auth/revoke` | `{ refreshToken }` | Revokes a token family/session |
| `POST /auth/password/forgot` | `{ email }` | Creates an expiring reset challenge without disclosing account existence |
| `POST /auth/password/reset` | `{ token, newPassword, confirmPassword }` | Validates token and password policy, resets password, revokes existing sessions |
| `GET /auth/me` | none | Current user, financer, roles, and permissions |
| `POST /auth/password/change` | `{ currentPassword, newPassword, confirmPassword }` | Changes the authenticated user's password and revokes existing sessions |

For financer login, `email` accepts either the registered email address or mobile number. Profile data is available through `GET/PUT /profile`.

## Core request/response models

### Financer

`FinancerResponse`: `id`, `financerNumber`, `legalName`, `displayName`, `ownerName`, `email`, `phone`, `address`, `city`, `state`, `postalCode`, `taxNumber`, `registrationNumber`, `status`, `kycStatus`, `serviceChargePercentage`, `createdAt`, operational counts and balances.

`CreateFinancerRequest`: legal/display names, owner details, email, phone, address, registration/tax identifiers, service-charge override. Status changes use `ChangeFinancerStatusRequest { status, reason }` and are audited.

### User/employee

`UserResponse`: `id`, `financerId`, `employeeNumber`, `firstName`, `lastName`, `email`, `phone`, `status`, `roles`, `lastLoginAt`, timestamps.

`CreateUserRequest`: financer scope, identity/contact data, initial password or invitation flag, role IDs. `UpdateUserRolesRequest` contains role IDs. Passwords are never returned.

### Customer and KYC

`CustomerResponse`: `id`, `customerNumber`, financer, name, DOB, gender, phone, email, full address, Aadhaar masked value, PAN masked value, `status`, `kycStatus`, active-loan count, outstanding amount, next due date, timestamps.

`CreateCustomerRequest` maps the frontend's four-step customer wizard: personal details; address; Aadhaar/PAN; optional uploaded documents. `UpdateCustomerRequest` edits mutable profile fields. Notes use `{ text }`.

`KycSubmissionRequest`: customer, identity type/number, declared name/DOB and document IDs. `KycDecisionRequest`: `{ status: Verified|Rejected|NeedsInformation, notes }`.

`DocumentResponse`: metadata only, including category, original file name, content type, size, hash, verification status, uploader/verifier, timestamps. Upload uses multipart form-data; download is authorized and streamed.

### Loan product/application/loan

`LoanProductRequest`: name/code, min/max principal, min/max tenure, annual rate, interest method, repayment frequency, processing fee, late-fee rules, eligibility limits, active flag.

`LoanApplicationRequest`: customer, product, requested principal, tenure, purpose, income, obligations and notes. Eligibility uses `{ customerId, productId, requestedAmount, tenureMonths, monthlyIncome, monthlyObligations }` and returns pass/fail, eligible amount, FOIR, age and KYC rule results.

`LoanApplicationResponse`: application number, customer/product, requested and approved terms, workflow status, eligibility result, assigned verifier, decision/rejection information, timestamps.

`LoanDecisionRequest`: approved amount/rate/tenure, decision notes. `RejectLoanRequest`: reason code and notes. `DisbursementRequest`: amount, date, bank reference, account details and mode.

`LoanResponse`: loan number, application/customer/product, principal, annual rate, interest method, tenure, dates, status, principal/interest outstanding, overdue values, next due, disbursement and summary fields.

### Schedule/payment/collection

`PaymentScheduleResponse`: installment number, due date, opening principal, principal, interest, fees, total due, total paid, balance, status, paid date.

`RecordPaymentRequest`: loan, optional schedule installment, amount, received date, mode, external reference, notes and allocation preference. Response includes generated receipt and principal/interest/fee allocation.

`ReschedulePaymentRequest`: schedule ID, new due date and mandatory reason; creates history and recalculates overdue status without silently changing paid installments.

`CollectionResponse`: loan/customer/financer, due and overdue amounts/days, assigned agent, last reminder, promise-to-pay date, collection status, settlement/reconciliation information.

### Other models

- Notification: title, message, type, channel, entity reference, read status and timestamps.
- Support ticket: ticket number, subject, category, priority, description, status, assignee and threaded messages.
- Setting: scope, key, typed value, description and concurrency token; secret values are write-only/masked.
- Audit log: actor, financer, action, entity type/ID, before/after JSON, IP, user agent, correlation ID and UTC timestamp.
- Standard report filters: financer, customer, loan/product, status, from/to dates and output format.

## Endpoint inventory

### Financers, users, roles, permissions

- `GET/POST /financers`; `GET/PUT /financers/{id}`; `POST /financers/{id}/status`; `GET /financers/{id}/usage`.
- `GET/POST /users`; `GET/PUT/DELETE /users/{id}`; `PUT /users/{id}/roles`; `POST /users/{id}/status`.
- `GET /admins`, `GET /employees` are role/scope-filtered user views.
- `GET/POST /roles`; `GET/PUT/DELETE /roles/{id}`; `PUT /roles/{id}/permissions`; `GET /permissions`.

### Customers, KYC, documents

- `GET/POST /customers`; `GET/PUT/DELETE /customers/{id}`; `POST /customers/{id}/notes`; `GET /customers/{id}/ledger`.
- `GET/POST /kyc`; `GET /kyc/{id}`; `POST /kyc/{id}/decision`.
- `POST /documents` (multipart); `GET /documents/{id}`; `GET /documents/{id}/content`; `POST /documents/{id}/verify`; `DELETE /documents/{id}`.

### Products and loan lifecycle

- `GET/POST /loan-products`; `GET/PUT/DELETE /loan-products/{id}`.
- `POST /eligibility/checks`; `GET /eligibility/checks/{id}`.
- `GET/POST /loan-applications`; `GET/PUT /loan-applications/{id}`.
- `POST /loan-applications/{id}/submit`; `/verify`; `/approve`; `/reject`; `/disburse`.
- `GET /loan-applications/{id}/history`.
- `GET /loans`; `GET /loans/{id}`; `GET /loans/{id}/schedule`; `POST /loans/{id}/recalculate-schedule`.

Allowed application transitions are `Draft -> Submitted -> EligibilityPassed/EligibilityFailed -> KycPending -> UnderVerification -> Verified -> Approved|Rejected -> Disbursed`. Disbursement atomically creates the loan, transaction, status history and EMI schedule. Terminal rejection and disbursement cannot be overwritten. Only authorized roles can verify, approve or disburse; the same-user maker/checker restriction is enforced for approval and disbursement.

### Payments, transactions, collections

- `GET/POST /payments`; `GET /payments/{id}`; `POST /payments/{id}/reverse`; `POST /payment-schedules/{id}/reschedule`.
- `GET /payment-schedules` provides the financer-wide interest schedule with paging, search, status and date filters.
- `GET /transactions`; `GET /transactions/{id}`; `POST /transactions/{id}/reconcile`.
- `GET /collections`; `GET /collections/{loanId}`; `POST /collections/{loanId}/assign`; `/reminders`; `/promise-to-pay`; `/status`.
- `GET /overdue-loans` with ageing buckets and due-date filters.

Payment allocation is fees, then overdue interest, current interest and principal unless a permitted allocation is explicitly supplied. Duplicate external references are rejected per financer. Recording/reversal updates schedules, loan balances, ledger transactions and collection state in one database transaction.

### Dashboard, communication, support, reporting and platform

- `GET /dashboard/financer`; `GET /dashboard/admin` with date range and optional financer filter.
- `GET /notifications`; `POST /notifications`; `POST /notifications/{id}/read`; `POST /notifications/read-all`.
- `GET/POST /support-tickets`; `GET /support-tickets/{id}`; `POST /support-tickets/{id}/messages`; `/assign`; `/status`.
- `GET /reports/portfolio`; `/collections`; `/payments`; `/overdue`; `/customers`; `/service-charges`; `/audit`; append `format=json|csv`.
- `GET/PUT /settings`; `GET/PUT /settings/{scope}/{key}`.
- `GET /audit-logs`; `GET /audit-logs/{id}` (read-only).
- `GET /health`; `GET /health/ready`; `GET /health/live`.

## Database and integration requirements

- Production database engine is currently unknown because SSH authentication to `root@187.52.115.32` failed. No database port, engine, database name, credentials, or schema was discovered.
- Local development uses SQLite only as a safe fallback. Provider registration is isolated in Infrastructure so it can be replaced after production discovery.
- Secrets are supplied by `ConnectionStrings__DefaultConnection`, `Jwt__Key`, and environment-specific secret providers; they never appear in committed configuration.
- File storage uses a local development directory behind an abstraction. Production should use protected object storage or an encrypted private volume.
- OTP delivery uses an abstraction. Development logs only a delivery event; production needs an approved SMS/email provider and must never return OTP codes.

## Non-functional requirements

- FluentValidation at the API boundary and domain invariant checks in services/entities.
- Structured JSON-compatible logging with correlation/trace IDs and no secret/PII logging.
- Global problem handling, cancellation-token support, optimistic concurrency where settings/configuration are edited, transactional financial workflows, and audit capture.
- Swagger bearer authentication, health checks, migration artifacts, unit and integration tests.
- Aadhaar/PAN and bank details must be encrypted or tokenized at rest in production and masked in ordinary responses.
